Visao geral

A ideia do experimento em uma frase

A mesma consulta ("listar pedidos com cliente e itens" / "buscar um produto") foi implementada de varias formas diferentes. Tudo o mais foi mantido identico — mesmo banco, mesmo volume de dados, mesma carga, mesma maquina — para que a unica variavel fosse a tecnica de otimizacao. Assim, a diferenca de desempenho observada e atribuivel a tecnica, e nao ao ambiente.

Como cada afirmacao e comprovada: toda resposta da API traz os headers X-Query-Count (quantos SQL aquela requisicao executou), X-Response-Time-Ms e X-Cache (HIT/MISS/BYPASS). Qualquer numero pode ser reconferido com um curl -i.

Como funciona

O caminho de uma requisicao e onde cada tecnica atua.

  curl / k6
     |
     v
  [ Filtro de diagnostico ]  <-- mede o tempo e conta os SQL da requisicao
     |                           devolve X-Query-Count / X-Response-Time-Ms / X-Cache
     v
  [ Controller ]
     |
     v
  [ Service ]---------> [ Redis ]      TECNICA 1: se o dado esta no cache,
     |                   (cache)       a requisicao termina aqui: ZERO SQL.
     |  (cache MISS)
     v
  [ Repository / JPA ]                 TECNICA 2: a estrategia de carregamento
     |                                 decide QUANTOS SQL serao emitidos.
     v
  [ datasource-proxy ]  <-- intercepta cada SQL e incrementa o contador
     |
     v
  [ PostgreSQL ]                       TECNICA 3: o indice decide se cada SQL
                                        varre a tabela toda ou vai direto.
As tres tecnicas atacam niveis diferentes do mesmo problema: o cache reduz o numero de requisicoes que chegam ao banco; a estrategia de consulta reduz o numero de SQL por requisicao; o indice reduz o custo de cada SQL. Por isso elas se somam em vez de competir.

Item 1 — Cache com Redis

O cache nao deixa a consulta mais rapida: ele evita a consulta.

O que foi cacheado, e por que

DadoFrequencia de leituraVolatilidadeTTLDecisao
Detalhe do produtomuito altamedia (preco/estoque) 60 scachear + invalidar no update
Lista de categoriasaltabaixissima 10 mincachear com TTL longo

A volatilidade e que define o TTL: quanto mais o dado muda, menor o TTL, porque o TTL e o tamanho maximo da janela em que um cliente pode receber um dado errado.

O ciclo HIT / MISS / invalidacao

 1) GET /api/produtos/10/com-cache  ->  X-Cache: MISS   X-Query-Count: 1
 2) GET /api/produtos/10/com-cache  ->  X-Cache: HIT    X-Query-Count: 0  <-- banco nao foi tocado
 3) PUT /api/produtos/10 {preco}    ->  grava no banco e REMOVE a chave do Redis
 4) GET /api/produtos/10/com-cache  ->  X-Cache: MISS   X-Query-Count: 1  (dado novo)
 5) apos o TTL                      ->  a chave expira sozinha; proxima leitura e MISS
A prova do cache e X-Query-Count: 0. Latencia menor poderia ser coincidencia de carga; zero SQL nao tem outra explicacao: a requisicao foi atendida sem o banco.
Escolhemos @CacheEvict (apagar) em vez de @CachePut (sobrescrever). O CachePut gravaria no cache o valor que a aplicacao supoe estar no banco; se houver trigger, default ou escrita concorrente, o cache passaria a servir um valor que nunca existiu. Apagando, a proxima leitura reconstroi a partir da fonte da verdade. Custo: um MISS extra. Beneficio: nao existe cache mentindo.

Resultado sob carga

Correcao de metodo (a medicao contrariou a hipotese): a variante hoje chamada com-cache-espalhado nasceu como "cache frio", para medir o custo do MISS. Ela nao faz isso. O hit ratio medido foi de 98,5%: com 2.000 IDs distintos e ~2.300 req/s, o cache aquece em 0,86 s de uma rodada de 25 s. Por isso as curvas "quente" e "espalhado" praticamente coincidem no grafico acima — as duas sao quentes. O que essa variante realmente mede e o efeito da cardinalidade das chaves (50 vs 2.000 IDs).

Teste de carga e a ferramenta errada para medir o custo do MISS: qualquer faixa de chaves que caiba na tabela aquece em menos de um segundo. A pergunta do item 3.5 e respondida por scripts/experimento-custo-miss.sh, que limpa o cache antes de CADA requisicao (100% MISS garantido): o MISS paga 3 idas (Redis + banco + Redis) contra 1 ida de quem nao tem cache.

Item 2a — LAZY vs EAGER e o problema N+1

O mesmo resultado, a mesma tela, numeros de SQL radicalmente diferentes.

SQL executado por requisicao (medido)

Por que o N+1 acontece

Em LAZY, o Hibernate devolve um proxy no lugar do objeto relacionado. O SQL extra so e disparado quando o codigo toca nesse proxy. Montar o DTO percorre cliente e itens de cada pedido — e cada acesso vira uma consulta:

 1  SELECT * FROM pedido ORDER BY id LIMIT 100          <- a "1"
 +  SELECT * FROM cliente      WHERE id = ?   x100      <- os "N"
 +  SELECT * FROM item_pedido  WHERE pedido_id = ?  x100
 +  SELECT * FROM produto      WHERE id = ?   x...
EAGER nao resolve o N+1. O enunciado pede para observar o comportamento real, e foi o que fizemos: com colecao EAGER numa consulta JPQL sem fetch explicito, o Hibernate traz os pedidos e depois resolve cada colecao — tambem em N consultas. A diferenca e que agora o custo e pago sempre, mesmo quando o endpoint nao usa os relacionamentos.
A vantagem real do LAZY aparece em /lazy-sem-acesso: nada e tocado, nenhuma query extra e emitida, e o contador fica em 1 independentemente do limite. LAZY e um bom default; o erro nao e o LAZY, e percorrer relacionamentos sem ter planejado como carrega-los.

Item 2b — Consultas otimizadas

Cinco formas de obter o mesmo DTO com um numero constante de SQL.

EstrategiaComo funcionaQuando preferir
JOIN FETCH uma query com join; os relacionamentos vem na mesma linha o caso geral; exige o padrao de 2 etapas quando ha paginacao
@EntityGraph mesmo plano do JOIN FETCH, declarado por atributos quando se quer reaproveitar a query variando o que carregar
@BatchSize agrupa os proxies em WHERE id IN (...) varias colecoes: evita o produto cartesiano do join
Projecao DTO le colunas soltas, sem criar entidades gerenciadas telas de leitura: menos CPU e memoria por requisicao
SQL nativo (json_agg) o banco monta o array de itens; 1 linha por pedido payload grande, onde as linhas repetidas do join pesam
Paginacao + JOIN FETCH de colecao: a armadilha. Com join de colecao, um pedido vira N linhas. Aplicar LIMIT direto cortaria no meio dos itens, trazendo pedidos incompletos — o Hibernate detecta isso e, para nao errar, traz tudo para a memoria e pagina em Java (aviso HHH90003004), o que anula o ganho. A solucao e o padrao de 2 etapas: primeiro os IDs da pagina, depois o JOIN FETCH por esses IDs.
SQL nativo compensou? Em numero de SQL, empata com JOIN FETCH (ambos constantes). Ganha em trafego, porque nao repete os dados do pedido em cada linha de item. Mas custa portabilidade (json_agg e PostgreSQL), perde a verificacao em tempo de compilacao e renomear coluna deixa de ser refatoracao automatica. Vale quando o gargalo medido e o volume de dados trafegado — nao por padrao.

Desempenho sob carga

Como NAO ler esta tabela: a diferenca entre lazy/eager e as cinco estrategias otimizadas e enorme e consistente (uma ordem de grandeza) — essa conclusao e solida. Ja o ranking entre as cinco otimizadas nao e estavel: com 25 VUs, por exemplo, o p95 do join-fetch foi 110,70 ± 51,65 ms, ou seja, o desvio entre repeticoes e maior que a distancia ate as concorrentes. Dizer "o EntityGraph e o mais rapido" seria ler ruido como resultado. Elas emitem o MESMO numero de SQL (2) e a escolha entre elas se decide por criterios de projeto (portabilidade, verificacao em tempo de compilacao, produto cartesiano com varias colecoes), nao por alguns milissegundos de diferenca.

Item 2c — Indices

A consulta nao mudou uma letra. Só o plano de execucao mudou.

SELECT * FROM pedido WHERE cliente_id = 150 ORDER BY data_pedido DESC LIMIT 50;

CREATE INDEX idx_pedido_cliente_data ON pedido (cliente_id, data_pedido DESC);

Por consulta-alvo (1a execucao descartada)

O que o EXPLAIN mostrou

Duas coisas melhoraram ao mesmo tempo:

  • Seq Scan → Index Scan: em vez de ler as 300.000 linhas da tabela e descartar quase todas, o banco vai direto as linhas daquele cliente.
  • O no Sort desapareceu: o indice foi criado como (cliente_id, data_pedido DESC), ja na ordem pedida pelo ORDER BY. Nao ha nada para ordenar em tempo de execucao — e por isso o indice composto rende muito mais que um indice simples em cliente_id.
Entao por que nao indexar todas as colunas? Indice nao e gratuito: (1) ocupa espaco em disco; (2) todo INSERT/UPDATE/DELETE precisa atualizar cada indice da tabela, o que torna a escrita mais lenta; (3) indice com baixa seletividade (ex.: status, com 5 valores distintos em 300 mil linhas) costuma ser ignorado pelo planner, pois ler o indice e depois buscar as linhas sairia mais caro que varrer a tabela. Indice se escolhe a partir das consultas reais — e se confere no EXPLAIN.

Item 3 — Testes de desempenho (k6)

Metricas obrigatorias: latencia media, p95, p99, throughput e taxa de erros.

Como ler estes numeros

  • VUs nao sao req/s. Um usuario virtual dispara requisicoes em sequencia; 10 VUs podem gerar centenas de req/s. Mais VUs = mais concorrencia, nao necessariamente mais vazao.
  • p95 e p99 importam mais que a media. A media esconde a cauda: um p99 muito acima da media revela que uma fracao dos usuarios tem uma experiencia bem pior — tipicamente fila por conexao do pool, pausa de GC ou contencao no banco.
  • Throughput que para de subir com mais VUs indica saturacao: o gargalo deixou de ser a concorrencia e passou a ser um recurso (CPU, conexoes, disco).
  • Aquecimento descartado: cada rodada roda duas vezes e so a segunda e exportada. A primeira serve para a JVM compilar (JIT), encher o pool de conexoes e aquecer o cache de buffers do Postgres.

Todos os resultados

O que muda o desempenho (e em que direcao)

Cada item abaixo e um parametro real do projeto. Altere, rode scripts/run-all-tests.sh e compare.

TTL do cache — app.cache.ttl-produto em application.yml
TTL maior = mais HIT = menos carga no banco, mas janela maior de dado desatualizado. TTL menor = dado mais fresco, menos HIT. Nao existe valor "certo": e a troca entre consistencia e custo, decidida pela volatilidade do dado.
Invalidacao ativa — profile cache-sem-invalidacao
Com @CacheEvict, a escrita corrige o cache na hora. Sem ela, o cache serve o valor antigo por todo o TTL. Rode scripts/experimento-cache-sem-invalidacao.sh para ver o preco errado sendo devolvido enquanto o banco ja tem o novo.
Estrategia de carregamento — endpoint escolhido
E a alavanca de maior efeito nas listagens: sai de centenas de SQL por requisicao (LAZY com acesso) para 2 (JOIN FETCH / DTO). Repare que o X-Query-Count do LAZY cresce com ?limite=, enquanto o das versoes otimizadas fica constante — essa e a diferenca entre complexidade O(N) e O(1) em numero de consultas.
?limite= — quantos pedidos por requisicao
Aumentar o limite nao muda o numero de SQL das estrategias otimizadas, mas aumenta o payload. No LAZY, multiplica tambem o numero de consultas: o tempo cresce bem mais rapido que o volume de dados retornado.
Indices — db/10-create-index.sql / 11-drop-index.sql
Ganho enorme na leitura filtrada e ordenada; custo em espaco e na escrita. A ordem das colunas no indice composto e decisiva: igualdade primeiro, intervalo/ordenacao depois.
Tamanho do pool de conexoes — spring.datasource.hikari.maximum-pool-size
Pool pequeno vira fila sob carga alta: a media sobe pouco e o p99 explode. Pool grande demais transfere a disputa para o banco (contencao de CPU e locks). E tambem por isso o pool esta fixo: pool elastico mudaria de tamanho entre rodadas e tornaria as comparacoes incomparaveis.
Log de SQL — profile sql-log
Excelente para explicar o N+1 ao vivo, pessimo durante medicao: o I/O do log entra no tempo de resposta e mascara o efeito real da otimizacao. Por isso ele vem desligado por padrao.
Limites de CPU/memoria dos containers — docker-compose.yml
Estao fixos de proposito. Sem teto, o Docker daria mais recursos numa rodada que noutra e a variacao do ambiente se misturaria ao efeito da otimizacao.
